# Internationalization (中文 / English)

Co-Engram ships with **bilingual support** out of the box. Tool descriptions, viewer UI, and system prompt injections are all localized. Chinese teams and English teams can use the same memory store with their preferred language.

## How it works

```
┌─────────────────────────────────────────────────────────────┐
│ Language resolution priority (highest → lowest):            │
│                                                             │
│   1. Runtime override                                       │
│      - MCP: CO_ENGRAM_LANGUAGE=zh                           │
│      - OpenClaw: plugins.entries.co-engram.config.language  │
│                                                             │
│   2. Persisted team-memory choice                           │
│      - ~/team-memory/.co-engram/config.json                 │
│      - Written by `co-engram init`                          │
│                                                             │
│   3. Default: zh (中文,面向中文团队的默认值)                  │
│      International teams set CO_ENGRAM_LANGUAGE=en or        │
│      language: 'en' in config.json.                         │
└─────────────────────────────────────────────────────────────┘
```

The default is **Chinese (`zh`)** since 0.2.0. The project is built primarily for Chinese teams, and `zh` makes the viewer UI, tool descriptions, and prompt sections Chinese out of the box without configuration. International teams opt out by setting `CO_ENGRAM_LANGUAGE=en` or `language: 'en'` in config.json.

## Picking a language on first use

The recommended way: use `co-engram init`.

```bash
co-engram init
# → Where should team-memory live? [default: ~/team-memory]
# → Choose language:
#     1. English (recommended for international teams)
#     2. 简体中文 (recommended for Chinese teams)
# → Default creator? [default: $USER]
```

The choice is persisted to `~/team-memory/.co-engram/config.json`:

```json
{
  "version": 1,
  "language": "zh",
  "defaultCreatedBy": "alice",
  "createdAt": "2026-06-21T...",
  "initializedBy": "co-engram-cli@0.1.0"
}
```

Both Claude Code (MCP) and OpenClaw (plugin) honor this file automatically.

## Overriding at runtime

You don't have to commit to one language forever. Override per-session:

### Claude Code (MCP)

```bash
claude mcp add co-engram \
  -e CO_ENGRAM_DATA_ROOT=$HOME/team-memory \
  -e CO_ENGRAM_LANGUAGE=zh \
  --scope user \
  -- co-engram-mcp
```

Or temporarily for a single run:

```bash
CO_ENGRAM_LANGUAGE=en co-engram-mcp
```

### OpenClaw (plugin manifest)

In your OpenClaw config (e.g. `~/.openclaw/config.yaml`):

```yaml
plugins:
  entries:
    co-engram:
      enabled: true
      config:
        dataRoot: /home/your/team-memory
        language: zh
```

## What gets translated

| Surface                                           | Example                                                                                                                                                                           |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool descriptions (30 tools, LLM-friendly format) | `engram_create` — "Create a new memory (engram) for important team knowledge. **WHEN TO CALL:** ..." / "为重要的团队知识创建新记忆(engram)。**何时调用:** ..."                    |
| Tool descriptions (fallback, developer-facing)    | Tools not yet in the LLM dict fall back to the core i18n string (e.g. `engram_archive` — "Archive an engram (move out of default retrieval, but data preserved and recoverable)") |
| Viewer UI                                         | "Co-Engram Viewer" / "Co-Engram 查看器"; buttons, tabs, loading messages                                                                                                          |
| System prompt injections                          | "3 memory candidates pending" / "3 个候选记忆待处理"                                                                                                                              |
| CLI prompts                                       | `co-engram init` welcome, language picker, next-steps hints                                                                                                                       |

### Two-tier tool descriptions

Co-Engram resolves tool descriptions in two layers, **shared across both hosts**:

1. **`LLM_TOOL_DESCRIPTIONS`** (in `@co-engram/core`) — structured "WHEN TO CALL / WHEN NOT TO CALL / RETURNS" descriptions for all 21 standard-profile tools (including the repository-health tools `engram_doctor`, `engram_list_paths`, and LLM synthesis `engram_synthesize`). These are what the LLM sees by default for the most-used tools.
2. **Core i18n dictionary** (`tool.*` keys) — shorter developer-facing descriptions for internal/admin tools (`engram_archive`, `skill_invoke`, …) that don't need the full LLM treatment.

Both the MCP server and the OpenClaw plugin adapter resolve through the same `resolveLlmDescription()` helper, so a Claude Code user and an OpenClaw user see identical descriptions for the same tool.

## What stays un-translated

- **Tool names** — always snake_case English (`engram_create`, `synapse_list`). LLM tool-call APIs expect stable identifiers; translating names would break agent integrations.
- **File layout** — `<domainTags>/<slug>.md`, `synapses/<kind>/syn-<hash>.yaml` etc. always English for Git friendliness.
- **Enum values** — `kind: fact` stays `fact` (not `类型: 事实`), `status: active` stays `active`, `extends` stays `extends`. These values are TypeScript literal-union types compared with `===` across ~25 consumers; translating them would break the type system. The YAML keys are localized (`类型:`, `状态:`, `类型: extends`), but the enum value stays English.
- **Runtime object field names** — when Co-Engram parses a file, the in-memory object always uses English keys (`{ id, title, kind, createdAt, ... }`) regardless of the disk format. The Chinese YAML keys exist only on disk for human reading; they normalize back to English on parse. This means none of the 25 consumer modules need to know about disk language.
- **Error messages from core engine** — runtime errors stay in English (developer-facing, not user-facing).
- **engram content itself** — the actual memories you write are whatever language you write them in. Co-Engram does not translate your data.

## Disk format vs runtime format

Co-Engram distinguishes **disk format** (what humans see when they open the file in an editor) from **runtime format** (what code sees after parsing).

In **English mode (`language='en'`)**, both are English:

```markdown
---
id: 01J...
title: Some fact
kind: fact
createdAt: 2026-06-21T...
---

body content
```

In **Chinese mode (`language='zh'`)**, the disk flips to body-on-top + Chinese keys + `__语言: zh` marker, but the runtime object is identical to English mode:

```markdown
body content

## <!-- co-engram-meta:zh -->

标识: 01J...
标题: Some fact
类型: fact
创建时间: 2026-06-21T...
\_\_语言: zh

---
```

Both formats parse to the same JavaScript object `{ id: '01J...', title: 'Some fact', kind: 'fact', createdAt: '...' }`. The Chinese keys are pure human convenience.

The first time a host starts with a new `language`, it runs `repository.migrateFormat(language)` which rewrites every file to the target format. See [data-format.md](./data-format.md#config-file-configco-engrayaml) for the `migratedToLanguage` mechanism.

## Adding a new language

Co-Engram currently ships `en` and `zh`. To add a third (e.g. `ja`):

1. Add the language code to `Language` type in [packages/core/src/i18n/types.ts](../packages/core/src/i18n/types.ts)
2. Create [packages/core/src/i18n/ja.ts](../packages/core/src/i18n/) mirroring the key structure of `en.ts`
3. Register it in `DICTIONARIES` in [packages/core/src/i18n/index.ts](../packages/core/src/i18n/index.ts)
4. Add it to `SUPPORTED_LANGUAGES`
5. Update `parseLanguage()` to recognize the new code
6. Add tests in [packages/core/test/i18n.test.ts](../packages/core/test/i18n.test.ts)

The dictionary has ~60 keys (25 tool descriptions + viewer strings + CLI prompts). A complete translation takes about an hour.

## Verification

After `co-engram init --language zh`:

```bash
# Restart Claude Code, then:
/mcp
# Tools listed — descriptions should be 中文

# Or via the viewer (if CO_ENGRAM_VIEWER_ENABLED=1):
curl http://127.0.0.1:18899/ | grep -o '<html lang="[^"]*"'
# → <html lang="zh">
```

## Design rationale

**Why bilingual natively, not via translation layer?**

- LLMs see the tool description verbatim. A poorly translated description degrades tool-call accuracy.
- Memory content is personal/team-specific. Forcing English on Chinese teams creates friction at every write.
- The "human-AI symbiosis" goal requires both sides to read comfortably — humans editing the engram Markdown body, AI calling tools.

See [design-rationale.md](./design-rationale.md) for the broader philosophy.
