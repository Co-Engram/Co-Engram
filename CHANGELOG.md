### Changed

- **`createdBy` is now fully system-decided across all write tools to stop the LLM from self-filling host identifiers (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: the LLM was self-identifying as `"claude-code"` via the MCP server name, and that value flowed straight through `parsed.createdBy ?? ctx.defaultCreatedBy ?? "unknown"` to overwrite the host-resolved git author — polluting team memory with host-software labels as the "author" of human-captured knowledge. Root cause: `createdBy` was an LLM-writable field, and the LLM had every incentive to fill it with its own runtime identity. Fix: `engram_create` / `synapse_create` / `engram_synthesize` / `engram_accept_proposal` / `engram_accept_proposals_by_source` now **ignore the LLM-passed `createdBy` entirely** — `void parsed.createdBy; const createdBy = ctx.defaultCreatedBy ?? "unknown";`. The `createdBy` schema field stays (marked `@deprecated`) for backward compatibility so older LLM tool calls don't error, but its value is dropped. The authority chain is unchanged: **local git identity (`user.name` → `user.email`)** → persisted team-memory config → `CO_ENGRAM_DEFAULT_CREATED_BY` env (MCP) / plugin config `defaultCreatedBy` (OpenClaw) → `'unknown'`. The OpenClaw plugin (`packages/openclaw-plugin/src/plugin-entry.ts`) is realigned from `config > git` to `git > config` to match the Claude Code MCP host — both hosts now share the same priority, and the existing `adapter.test.ts` cases are updated to assert `detectGitAuthor() ?? config-value`. **One deliberate exception**: `external-markdown` proposals preserve `payload.createdBy` (the external document's original author parsed from frontmatter) at the `ProposalEngine.accept` / `acceptBatch` layer — that value is file content (a fact), not LLM self-fill, and dropping it would lose provenance of imported docs; the `conversation` and `auto-memory` sources continue to ignore `payload.createdBy` and route through `ctx.defaultCreatedBy`. **For LLM-generated provenance** (e.g. "captured by Claude Code during a debug session"), the correct channel is the existing `encodingContext` field — `createdBy` stays a human-responsibility field. Docs synced bilingually: `docs/tool-reference.md` + `docs/tool-reference.zh-CN.md` (engr am_create / synapse_create / engram_accept_proposal createdBy descriptions), `docs/host-claude-code.md` + `docs/host-claude-code.zh-CN.md` (`CO_ENGRAM_DEFAULT_CREATED_BY` priority rewritten to match code), example frontmatter in `README.md` + `docs/data-format.md` + `docs/data-format.zh-CN.md` flipped from `createdBy: claude-code` to `createdBy: Yang Yang` to stop seeding the bad pattern. Tests: `packages/core/test/default-created-by.test.ts` rewritten — the engram_create / synapse_create / accept_proposal blocks now assert complete-override behavior (LLM passes `"claude-code"` → ignored; LLM passes `"Yang Yang"` → also ignored; ctx.defaultCreatedBy wins); `packages/core/test/tools-audit.test.ts` drops `createdBy: "alice"` from the synapse audit `toMatchObject` (not the test's concern); `packages/core/test/tools.test.ts` engram_list createdBy-filter test uses two inline `{ ...ctx, defaultCreatedBy }` spreads to seed distinct authors; `packages/openclaw-plugin/test/adapter.test.ts` asserts `detectGitAuthor() ?? config-value`; all 2285 core tests + 277 claude-code-mcp tests + 119/120 openclaw-plugin tests green (the one remaining `memory-tools.test.ts > minScore` failure is pre-existing hash-embedder behavior unrelated to this change).

(2) `packages/claude-code-mcp/src/hooks/installer.ts` `DEFAULT_VIEWER_URL` changes from `http://127.0.0.1:18799` to `http://127.0.0.1:18899` (this is the URL injected into Claude Code's `settings.json` env block so the `observe.py` hook can find the proposal engine's `/api/observe` endpoint). (3) `packages/claude-code-mcp/src/hooks/observe.py` default `CO_ENGRAM_VIEWER_URL` falls back to `http://127.0.0.1:18899`. (4) `packages/core/src/i18n/zh.ts` and `en.ts` `viewer.help.opsPorts` rewritten to explain the unified port + legacy-port migration. (5) `packages/openclaw-plugin/openclaw.plugin.json` capability descriptions and `uiHints` help text updated. (6) Docs synced across both languages: `README.md`, `README.zh-CN.md`, `docs/host-claude-code.md`, `docs/host-claude-code.zh-CN.md`, `docs/host-openclaw.md`, `docs/host-openclaw.zh-CN.md`, `docs/observability.md`, `docs/observability.zh-CN.md`, `docs/faq.md`, `docs/faq.zh-CN.md`, `docs/i18n.md`, `docs/i18n.zh-CN.md`, `packages/viewer/README.md`, `packages/openclaw-plugin/README.md`. **Migration for existing users**: anyone who bookmarked `http://127.0.0.1:18799` (Claude Code default) should update the bookmark to `http://127.0.0.1:18899`; the `CO_ENGRAM_VIEWER_PORT` env var still overrides both hosts for users running two separate dataRoots side-by-side. **Backward compatibility**: the persisted `viewer.port` field remains deprecated (unchanged); no behavior change for users who already pinned a custom port via env. **Tests**: existing `packages/viewer/test/viewer-port-warn.test.ts` continues to pass (it uses an env-pinned safe port `19345`, unaffected by the default change); `packages/viewer/test/viewer-accessibility.test.ts` comments are updated to reference `18899` (no assertion changes — the EADDRINUSE retry behavior is host-port-agnostic).

- **Audit tab `load()` destructuring bug fixed + `activeEngrams` KPI + `deleteSynapsesTouching` SQLite fast path + trash partition localization (`@co-engram/core`, `@co-engram/viewer`)**: four user-reported usability fixes landing together because each caused a "basic-functionality-broken" symptom. (1) **Audit tab stuck on `加载审计日志中…`** — `CO_ENGRAM_AUDIT.load()` in `packages/viewer/src/runtime/tabs.ts` read `[, engramsData] = await Promise.all([CO_ENGRAM._auditPager.load(), CO_ENGRAM.apiGet('/api/engrams/ids')])` but the destructuring `[engramsData]` grabbed the _first_ element (`pager.load()`'s resolved value — `undefined`, since paginator's `_load()` has no return) instead of the _second_ (the ids response). The next line `new Set(engramsData.ids || [])` threw `Cannot read properties of undefined (reading 'ids')`, the async handler rejected through `onTabEnter`'s `.catch`, and the timeline element kept its initial `加载审计日志中…` placeholder forever. Fix: `[, engramsData]` skips the paginator slot. Verified via Puppeteer headless load: all 10 tabs switch cleanly with zero console errors; audit timeline renders 100 rows in ~150ms wall (timing chip reports `filter 0.3ms · render 10.1ms · DOM 6.5ms` warm). (2) **`activeEngrams` field on `/api/stats` + dual-number KPI** — `StatsResponse` gains `activeEngrams: number` (SQLite `SELECT count(*) FROM engrams WHERE status = 'active'`, with memory-mode fallback via `byStatus.active`); the viewer's stats KPI now renders `activeEngrams / totalEngrams` (e.g. `1020 / 1026`) whenever `archived + forgotten > 0`, with hover tip explaining the dual numbers. Real-world driver: after restoring a `forgotten` engram from trash, `totalEngrams` is unchanged but `activeEngrams` increments by 1 — previously the single-number KPI made users think "restore did nothing." The sub-line now reads `活跃记忆数 N · 点击查看全部`. (3) **`deleteSynapsesTouching` SQLite fast path** — the previous implementation called `listSynapsesForEngram(rootPath, engramId)` (which internally `collectAllSynapses` scans every yaml under `synapses/`, ~45s at 1827 files) plus `deleteSynapsesTouching(rootPath, engramId)` (another full scan). In a `purgeAll` flow batch-deleting 267 engrams, each `deleteEngram` cascaded through this method, total wall ~6.7 hours, and users reported "永久清空失败" (purge-all button seems to hang). The new path: when `indexDb` is available, `listSynapsesForEngramFromIndex(engramId)` runs two `SELECT id, from_id, to_id, kind, weight FROM synapses WHERE from_id = ?` / `… WHERE to_id = ?` queries hitting the `synapses(from_id, to_id)` composite index — O(log N) instead of O(N) scan — then `deleteSynapseFile` only the few matching yaml files (SQLite rows fall through `ON DELETE CASCADE` when `deleteEngram` runs next). Total 267-engram purge: ~1 second. Memory-mode fallback stays on the old scan path (small warehouses, bounded cost). (4) **Trash partition labels localized** — `forgotten` and `archived` partition options in the trash tab previously showed raw English enum names; `formatPartitionLabel` / `formatPartitionTip` now route them through `T.enumLabel` + new `viewer.trash.partitionSweptSuffix` / `partitionTipSwept` keys (zh + en), with hover tips distinguishing soft-delete (`partitionTipSoft`) from swept-delete (`partitionTipSwept`). Existing i18n keys (`viewer.trash.colTitle` / `sourceSoft` / `sourceSwept` / `loadMore` / `allLoaded` / `partitionSoftSuffix`) were already in tree via an earlier commit; this entry adds the `formatPartitionLabel` / `formatPartitionTip` rendering glue in `tabs.ts` plus the `partitionTipSoft` / `partitionTipSwept` keys.

- **`findExactHashMatch` / `buildHashIndex` N+1 `readEngram` eliminated via `listEngramIndex` + `exists` (`@co-engram/core`)**: `engram_create` calls `checkDuplicateSync` → `findExactHashMatch` to short-circuit on identical `contentHash`. The previous implementation looped `repo.listEngrams()` (returns `EngramCatalogEntry[]` without `contentHash`) then `repo.readEngram(entry.id)` per entry to fetch the hash — at 1026 engrams each `readEngram` is `readFileSync` + YAML parse + `assembleEngram` (which itself scans the `synapses/` directory), pegging one core at 60%+ CPU continuously when Claude Code VSCode auto-spawns a non-holder mcp-server and the agent loop repeatedly invokes `engram_create`. A CPU profile of the stuck non-holder (`/tmp/co-engram-1322534.cpuprofile`) showed ~100% of self-time in the YAML parser path (`parse/parser.js`, `parse/lexer.js`, `compose/*`) with parent chain `readEngram` ← `findExactHashMatch` ← `checkDuplicateSync` ← `engram_create.execute`. The new path calls `repo.listEngramIndex()` — `EngramIndexEntry` (from `engram-index.json`, maintained by `createEngram` → `buildIndexEntryFromFrontmatter` → `updateIndexEntry`) already carries `contentHash`, so the hash comparison is an O(n) memory walk with no `readEngram` cost — plus `repo.exists(entry.id)` per match for the F2 stale-entry guard (single `existsSync`, O(1) stat, vs ~30ms `readFileSync` + parse per call). At 1026 engrams the new path measures ~50ms (vs 30+s), a 600x speedup. F2 stale-entry tolerance is preserved by the `exists` check (the reason `listEngramIndex` alone is insufficient — it does not filter "index entry exists but disk file gone" orphans left by partial `deleteEngram` failures). The earlier in-source comments claiming "P1 simplified linear scan, P2 will introduce hash → id index" and "代价是 N 次 fs 读,可接受" are removed — they were wrong at 1k+ scale. Tests: all 4 stale-entry cases in `packages/core/test/dedup.test.ts` pass unchanged (F2 contract intact); full core suite (2085 tests) green; live monitor across 3 light-stage boundaries over 10 minutes shows holder pcpu stable at 3.1–3.3% with every `/`, `/api/stats`, `/api/audit`, `/api/proposals` returning 200 in <100ms before/during/after each stage fire.

- **`computePromptSignals` N+1 `readEngram` eliminated via `readDigestBatch` (`@co-engram/core`)**: the maintenance light stage (5-min `setInterval`) calls `computePromptSignals(repository, …)` to refresh the prompt-builder's `lowConfidenceTopics` input. The previous implementation looped `repository.readEngram(entry.id)` for every catalog entry — at 1026 engrams each `readEngram` is `readFileSync` + YAML parse + `assembleEngram` (which itself scans the `synapses/` directory), and the loop synchronously blocked the gateway's single-threaded event loop for 30+ seconds. Real-world symptom: the viewer's HTTP endpoints were healthy in the first 5 minutes after `mcp-server` boot, then every `curl http://127.0.0.1:18799/...` started returning `000` (timeout) exactly when the light stage first fired, and stayed unresponsive until the stage finished. CPU pegged at 90%+ on one core, ProcessLock heartbeat starved, and external clients (curl, browser) saw the gateway as dead. The fix has two parts. (1) **`DigestLine` interface gains `confidence: number`** — the SQLite `engrams` table and `DigestIndexRow` already carried `confidence` (since schema v2), but the public `DigestLine` interface and the `digestRowToLine` mapping silently dropped it, so callers needing `confidence` had no batch path and were forced back to `readEngram`. The field is now projected by `digestRowToLine` (SQLite mode), `readDigestLine` (single-id helper in `index/digest-builder.ts`), and the `readDigestBatch` memory-mode fallback. One in-repo caller constructing a `DigestLine` literal by hand (`readEngramViewAuto` in `packages/core/src/tools/engram-tools.ts`) is updated to pass `confidence: 0` (the value is unused downstream by `adaptiveDisclosure`). (2) **`computePromptSignals` now batches via `repository.readDigestBatch(ids)`** — 500 ids per call (the API's per-call upper bound) so a 1026-engram warehouse is two SQL `WHERE id IN (?,?,…)` round-trips instead of 1026 `readEngram` calls. SQLite mode measures ~25ms total (1000x+ speedup over the 30+s N+1); memory-mode fallback still walks `readEngram` per-id but only matters for tiny warehouses where the cost is bounded. The previous "代价是 N 次 fs 读,light stage 5 分钟一次可接受" comment is removed — it was wrong at 1k+ scale. Tests: all 11 cases in `packages/core/test/prompt-signals.test.ts` pass unchanged (the public contract is identical); full core suite (2085 tests) green; manual live verification confirms the viewer stays responsive across the light-stage boundary (every 30s curl sample returns HTTP 200 in <50ms before, during, and after the stage fires).

- **Audit log now self-rotates by action value tier + file size hard cap, decoupled from the maintenance engine (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: previously `.co-engram/audit.jsonl` was append-only with no expiry — at sustained tool-call throughput (1000+ engrams × daily propose/reinforce/importance*update events) the file grew unbounded, and the existing `index-cleanup.ts` code path explicitly skipped it with a "不应清理" comment. The new rotation mechanism lives entirely on `AuditLog` and runs as an **independent background `setInterval`** (default 24h, `intervalMs` configurable), explicitly decoupled from the maintenance engine's light/deep/rem/daily stages per the design directive that "日志管理与 engram 数据维护是不同概念的东西". Two-axis retention: (1) **Action value tiering** — `HIGH_VALUE_ACTIONS` (create / update / update_lifecycle / importance_update / forget / restore / sweep_to_trash / restore_from_trash / purge / accept / dismiss / contradicted / merge*_ / learning*loop*_) retain `highValueRetentionDays` (default 365d); everything else (propose / reinforce / report*failure / retrieve*_ / noise*filtered / necessity_rejected) retains `retentionDays` (default 90d). (2) **File size hard cap** — even when no time threshold has tripped, `maxSizeMb` (default 50MB) forces tail-truncation (walk from the file's end, accumulate lines until the budget is exhausted) so `readFileSync` can never blow up on a runaway audit file. **Atomic write** via `tmp-${pid}-${ts}` + `renameSync` prevents partial-flush corruption. **Corrupt-line preservation**: lines that fail JSON.parse or have unparseable `ts` are kept verbatim, not silently dropped — hand-off to `engram_audit_query` / human review. **Failure mode is fail-soft**: every IO/JSON exception returns `{droppedCount: 0, originalSize, newSize: originalSize}` instead of throwing, and the rotation action itself never writes an audit entry (would be self-reinforcing noise). **Host wiring**: `createCoEngramMcpServer` and `registerCoEngramTools` both start the rotator after `auditLog` construction (skipped when `auditEnabled=false`), each returns a `stopAuditRotation` fn that the Claude Code MCP `shutdown` handler calls alongside `stopMaintenance` / `stopIndexWatcher`; the OpenClaw plugin relies on the timer's `unref()` for OS-level cleanup. **New types/exports**: `AuditRotationConfig` extracted as named interface (was inline in `AuditSectionConfig`); `DEFAULT_AUDIT_CONFIG` + all `DEFAULT*_\_CONFIG`constants now re-exported from`@co-engram/core`public surface;`CoEngramMcpServerConfig.auditRotationConfig`and`CoEngramPluginConfig.auditRotationConfig`added (optional, falls back to`DEFAULT_AUDIT_CONFIG.rotation`). **Comment in `index-cleanup.ts`updated**: the stale "不应清理" note is replaced with a pointer to the new`AuditLog.startAutoRotation`path. **9 new tests** in`packages/core/test/audit-rotation.test.ts`lock the matrix (retentionDays drops low-value expired / highValueRetentionDays keeps old accept / maxSizeMb truncates tail-newest / corrupt-line preservation / noop when nothing to drop / empty-file no-throw / missing-file no-throw /`intervalMs<=0`returns noop-stop /`intervalMs>0` returns valid stop).

- **`engram_doctor` now detects and (conservatively) auto-fixes frontmatter value validation issues (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: previously the doctor only repaired the _file layer_ (moved files / title renames / missing files / orphan markdown / dangling synapses) and the _infrastructure layer_ (missing derived indexes / merge driver) — but it never inspected the _value layer_ of the YAML frontmatter itself, so hand-edited or migration-drifted engram files with malformed values passed silently through to retrieval, viewer, and graph rendering. The new validation lives in `parseEngramFile` (the truth source for frontmatter parsing in `packages/core/src/storage/engram-store.ts`) and runs after delocalization, covering 7 categories: `type_mismatch` (numeric fields `importance` / `confidence` / `effectiveness` / `decayRate` / `weight` / `reinforcementScore` / etc. stored as strings, `createdAt` / `updatedAt` / `lastSeen` stored as strings, `domainTags` / `contextTags` / `kinds` stored as single non-array values), `out_of_range` (numerics outside `[0,1]` for `importance` / `confidence` / `effectiveness` / `decayRate` / `weight`, `importance` outside `[0,1]` for clamping), `invalid_enum` (`kind` / `status` / `visibility` / `sourceType` / `freshness` / `verificationState` against their closed-code unions — `visibility: leaked` and `status: corrupted` are flagged `critical` because fail-open `VIS_STRICTNESS` undefined → `maxVisibility` returns the most-permissive value → security-relevant leak), `invalid_format` (ULID id field malformed, ISO8601 date fields unparseable — severity `critical` for id because the ULID is the cross-reference key), `missing_required` (`id` / `title` missing — `critical`), `unknown_field` (frontmatter key not in the known schema), `derived_mismatch` (`contentHash` / `contentSize` stale relative to the body — auto-recomputable via identity `mutateFrontmatter` which re-runs `computeContentHash`). **Three new `DoctorIssue.kind` values** extend the existing closed union: `invalid_frontmatter` (YAML syntax error from the parser, reported separately from orphan markdown), `invalid_field_value` (per-field issue — message + severity distinguish the 7 sub-categories, no per-kind split per design decision), `derived_field_stale` (kept as a distinct kind because it's always auto-fixable and the viewer's doctor card labels it differently). **`parseEngramFile` no longer throws on missing id/title or invalid values** — it captures issues into a private `_validationIssues: readonly ValidationIssue[]` field on `EngramFile` and returns normally. Five YAML structural errors (missing `---` delimiter / mixed delimiters / unclosed frontmatter / non-mapping YAML / bottom-marker without closing `---`) still throw — they are unrecoverable parser errors, not value errors, and the new `hasFrontmatterMarker()` helper lets `engram-index.ts` route them to `onInvalidFrontmatter` (instead of `onOrphan`) so the doctor reports them with a precise nextAction hint rather than mislabeling them as orphan markdown. **`isEngramFile` semantics tightened** — previously "does it parse without throwing?", now "parses AND no critical validation issue"; this blocks files with `visibility: leaked` or missing id from entering the canonical `engram-index.json` rather than entering and silently failing downstream. **Auto-fix policy is conservative** (per the design's "诊断为主,自动修复保守型" directive): only `derived_mismatch` (contentHash/contentSize recompute via identity `mutateFrontmatter`), `out_of_range` numerics that are clampable (`importance` / `confidence` / `effectiveness` / `decayRate` / `weight` clamped into `[0,1]`), and `unknown_field` removal run automatically — everything else (invalid enum, malformed ULID, missing required, YAML syntax) is reported with a precise `nextAction` hint pointing the LLM / user at the right tool (`engram_update` with field=value, or manual repair). **`runDoctor` integration**: after the index rebuild, the doctor walks every entry, reads `_validationIssues`, and routes through `processValidationIssues(stableId, relativePath, issues)` which batches all auto-fixable issues for one file into a single `mutateFrontmatter` call (one fsync per file, not per issue). The `onInvalidFrontmatter` callback re-parses the raw file to extract field-level issues even when top-level YAML parsing threw, so the nextAction hint for a YAML syntax error can still name the offending field when recoverable. **Next-action templates** in `nextActionFor(issue, stableId)` produce actionable hints like `engram_update with id=<id>, visibility="public"` (invalid_enum visibility), `engram_update with id=<id>, kind="observation"` (invalid_enum kind), `manual repair: re-parse YAML in <path>` (invalid_frontmatter syntax), `engram_update with id=<id>, id=<new-ulid>` (invalid_format id — this is a manual fix because changing the ULID requires cascading synapse rewrites). **Watcher does NOT auto-trigger doctor** per design — the watcher continues to fire the existing `onOrphan` / `onExternalChange` paths; the value validation runs on the next scheduled or user-invoked doctor scan, keeping the watcher's latency profile untouched. **No external API change** — `engram_doctor`'s input/output shapes are unchanged; the `issues[]` array simply gains new `kind` values, and the `description` field is updated to mention the new coverage so the LLM knows to invoke `engram_doctor` for hand-edited-file symptoms. Both hosts (`@co-engram/claude-code`, `@co-engram/openclaw`) inherit the validation through the shared `@co-engram/core` — no adapter changes needed beyond rebuilding `dist`. **Tests**: 16-case validation suite in `packages/core/test/engram-store.test.ts` (covers all 7 categories + normalization round-trips), 9-case behavioral suite in `packages/core/test/doctor-frontmatter-fix.test.ts` (out_of_range clamp / unknown_field removal / derived_mismatch recompute / invalid_enum kind+visibility / invalid_format / missing_required / invalid_frontmatter YAML / batch mixed), 5-case `hasFrontmatterMarker` suite, 5-case `invalid_frontmatter 分流` suite in `packages/core/test/engram-index.test.ts` (YAML-error routing through the new callback). Full `@co-engram/core` suite (2094+ tests) green.

- **Viewer `GET /api/engrams` rewritten from N+1 `readEngram` loop to a single SQL query (`@co-engram/core`, `@co-engram/viewer`)**: at 1k+ engram scale the viewer's list endpoint was effectively unusable — the previous implementation called `repository.listEngrams()` (returns `EngramCatalogEntry[]` without `summary` / `importance` / `retrievalCount` / `visibility`) and then issued one `repository.readEngram(id)` per row to assemble the response payload. Each `readEngram` is a sync `readFileSync` + YAML parse + delocalize-keys pass, so 1k engrams ≈ 1k syscalls on the gateway's single-threaded event loop, blocking MCP tool calls and HTTP requests alike for 30+ seconds. Real-world symptom: after a load test seeded 1000 engrams, `curl /api/engrams` returned `000` (8s timeout) and the gateway process pegged one core at 95%+ CPU for minutes. The fix has three parts. (1) **Schema v2** for the derived `index.db`: the `engrams` table gains three columns that were previously only on the file's frontmatter — `summary TEXT NOT NULL DEFAULT ''`, `retrieval_count INTEGER NOT NULL DEFAULT 0`, `created_at INTEGER NOT NULL DEFAULT 0` — plus two indexes (`idx_engrams_created ON engrams(created_at DESC)` and `idx_engrams_retrieval ON engrams(retrieval_count DESC, updated_at DESC)`). A new `schema_version` table tracks the active version; on `IndexDb.open()` any version mismatch triggers a `DROP TABLE engrams` + full rebuild (SQLite is derived data, so DROP+rebuild is simpler and safer than `ALTER TABLE … ADD COLUMN`). `BootstrapResult.indexDb` is held by the host so it can be `close()`'d explicitly. (2) **`IndexDb.queryEngrams()`** replaces the per-row `readEngram` calls with one parameterized SQL query: `WHERE` clause filters by domain tags, kind, status, freshness, importance range; `ORDER BY` supports `updatedAt` / `createdAt` / `importance` / `retrievalCount` (each DESC + `id ASC` tiebreaker for stable pagination); `LIMIT ? OFFSET ?` (or cursor-keyed for pagination). Two new helpers, `encodeQueryCursor(sortValue, id)` and `decodeQueryCursor(cursor)` (named separately from the existing `encodeCursor` in `index-db-cursor.ts` because the cursor encoding is sort-key-specific), produce opaque base64url tokens stable across concurrent writes. (3) **`EngramRepository.queryEngramsForList()`** is the new public method the viewer calls — when `indexDb` is injected (sqlite engine active) it proxies directly to `IndexDb.queryEngrams()`; when not (memory fallback), it assembles the same `{ results, total, nextCursor }` shape from the in-memory path. The viewer's `GET /api/engrams` handler now calls `ctx.repository.queryEngramsForList(...)` and returns the cursor as `nextCursor`; default `limit=200`, max `limit=500`. The cold-start rebuild in `bootstrapRepositoryAndSearch()` also feeds the three new columns via `engramToIndexEntry()` so a fresh `index.db` against a non-empty warehouse is immediately sortable by `createdAt` / `retrievalCount`. **Measured impact** (1446 engrams indexed, `limit=500`): P50 ≈ 5ms, P95 ≈ 13ms, max ≈ 22ms — versus the previous 30+ second hang at 1k scale. Cursor pagination round-trip (`?limit=3&cursor=…`) adds <3ms. FTS search (`/api/search`) is unaffected (already sqlite-backed) and stays in the 3–22ms range. The viewer's frontend (`packages/viewer/src/runtime/tabs.ts`) caches `data.total` from the first page so the count chip renders the true total immediately; the audit tab drops its previous `?limit=10000` hack and uses the default paginated query. Note: this fix targets the _list_ path; the graph tab's `buildGraph` still uses N+1 over the synapse layer and will be addressed separately.

- **Default search engine flipped from `memory` to `sqlite` with fail-safe fallback (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: `resolveSearchEngineType()` now defaults to `sqlite` and treats only the literal `CO_ENGRAM_SEARCH_ENGINE=memory` as opt-out (was: defaulted to `memory`, opt-in via `=sqlite`). Unknown env values now fall back to `sqlite` (was: `memory`) — a typo no longer silently downgrades you to the less-scalable backend. - **`SqliteSearchOrchestrator` bm25 scores now normalized to [0, 1] as the `SimpleSearchResult.score` contract documents (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: the in-memory `SearchOrchestrator.search()` has always run `clamp01(rawScore)` before returning scores, but the SQLite FTS5 path (the Phase 2 engine that production deployments now use) had an inline comment saying "Phase 2 保留原始 bm25 数值(让排序语义清晰),上层工具层负责 clamp/解释" and skipped normalization entirely — the upper tool layer had no such clamp either, so `engram_search` returned scores like `26.62346925036157`, directly violating the `SimpleSearchResult.score` JSDoc promise that scores are "严格 ∈ [0, 1]". Real-world symptom: an LLM calling `engram_search("co-engram")` against a 1026-engram warehouse saw `score: 26.6` on the top hit, then either (a) treated it as a confidence to compare against thresholds calibrated for [0,1], or (b) echoed the raw number to the user as "26.6× match" — both unacceptable. The fix mirrors the in-memory pattern: after `applyPostFilter`, compute `maxScore = max(filtered.map(r => r.score))` (or 0 if empty), then divide every row's score by it so the top hit normalizes to 1.0 and the rest scale proportionally; ordering is unchanged (the max is the top hit, which stays ≥ the rest after normalization). Semantic trade-off acknowledged in source: cross-query absolute bm25 strength is lost (query A top=10 vs query B top=2 both normalize to 1.0), but this is the same trade-off the in-memory path already makes, and the gain is host symmetry + an LLM-readable score range that supports threshold-based routing. 4 new tests in `packages/core/test/retrieval/sqlite-orchestrator.test.ts` cover: multi-hit FTS where top hit = 1.0 and all scores ∈ [0,1], LIKE fallback where all scores stay 0, single-hit where self-division yields 1.0, and post-filter-drops-top-hit where the survivor re-normalizes to 1.0. ## [0.1.5] - 2026-07-03

### Changed

- **Trust boundary redesign: data-root `.md` files now become proposals (not engrams) on watcher fire, while `git pull` is trusted as an explicit user action (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: previously the `dataRoot` recursive watcher treated any `.md` write under the data root as a "create engram" trigger — but a watcher firing on a file the user did not hand-author (an external tool, an LLM recovering from a crash, or `git pull` checking out a teammate's commit) is not the same trust tier as a deliberate `engram_create`. Two failure modes followed: (1) `git pull` checked out a teammate's commit but the watcher re-proposed every incoming `.md` (or worse, raced with `git pull` mid-checkout), polluting the proposal queue with duplicates of engrams that already existed; (2) when a stale-state file under `dataRoot` was rewritten by an external process, the watcher again re-proposed it, defeating the user's dismiss intent. New `ProposalEngine.proposeExternalMarkdown()` is the single entry point for "I observed a `.md` file the user did not hand-author" — it writes a pending proposal (`source: "external-markdown"`, `slug` derived from path) instead of an engram; the existing watcher in `packages/claude-code-mcp/src/memory-sync/sync-engine.ts` and `packages/openclaw-plugin/src/plugin-entry.ts` now route `.md` writes through this method. The `createExternalMarkdownHook` helper installs the recursive watcher on `dataRoot` (filtering out `.co-engram/` subdirectory to avoid watching the index/proposals/audit files). `engram_accept_proposal` now allows omitting `title` / `content` / `domainTags` when the proposal carries a payload (external-markdown source), with the same fallback semantics as auto-memory proposals. The `Proposal` interface gains `source: "external-markdown"` as a new value alongside `"conversation"` / `"auto-memory"`; existing entries without the field are read as `"conversation"` (backwards compatible).

- **Post-merge git hook now runs `engram_doctor` so the canonical index reflects the teammate's commit before any other tool reads it (`@co-engram/core`)**: previously after `git pull` checked out a teammate's commit, `engram-index.json` was whatever the local repo had before the pull — so `engram_search` returned stale results, `engram_get` could miss just-pulled engrams, and the viewer showed a confusing mix of pre- and post-pull state until the next maintenance cycle. New `runPostMergeHook()` in `packages/core/src/merge/post-merge-hook.ts` runs after a successful `git pull` and (1) re-reads `engram-index.json`, (2) calls `runDoctor()` + `runInfraDoctor()` + `cleanupDanglingIndexReferences()` so any moved / renamed / deleted-by-teammate files are reconciled into the canonical index and derived indexes, (3) logs a summary. The hook is wired into the same `git` config slot as the merge driver; both hosts trigger it via the `git pull` wrapper in `repository.ts`. Combined with the watcher-redesign above, the new contract is: **`git pull` is trusted (it's an explicit user action); filesystem watcher is not trusted (it's ambient observation)**.

### Fixed

- **Three fail-silent bugs around `engram_delete` (`@co-engram/core`, `@co-engram/viewer`)**: user reported that `engram_delete` returned `{deleted: true}` but the entry stayed visible in the viewer — close inspection uncovered three distinct fail-silent failure modes clustered around the delete path. (F1) **`engram_delete` tool now post-checks the deletion**: when `repository.deleteEngram()` silently no-ops (cross-process race restores the file, `resolvePath` returns `undefined`, etc.) the tool previously returned `{deleted: true}` and wrote a misleading `purge` audit; it now re-checks `repository.exists(id)` after the call and throws `engram_delete failed: <id> still exists after deleteEngram (…run engram_doctor to self-heal)` so callers know to self-heal rather than trust a fake success. (F2) **`findExactHashMatch` / `buildHashIndex` now skip stale index entries**: when an engram file is removed externally but the index entry lingers (post-crash / partial delete), the previous `readEngram(entry.id)` threw and either aborted the whole dedupe pass or returned the dead id as a `DUPLICATE` target — locking the user out of recreating an engram with the same `contentHash`. Both functions now guard with `repo.exists(entry.id)` + try/catch around `readEngram`, skipping stale entries so dedupe falls through to similarity recall or `NEW`. (F3) **`deleteEngram` order changed from `file → synapse → index` to `index → file → synapse`**: the old order's mid-failure state left the index entry pointing at a deleted file (`dangling_index_entry`), which `doctor`'s `missing_file` check requires the file to actually be gone to detect — so a race that restored the file hid the inconsistency. The new order guarantees the index is clean when `deleteEngram` returns; any partial failure now lands in `doctor`-self-healable territory (`orphan_markdown` / `dangling_synapse`). The viewer's `DELETE /api/engrams/:id` endpoint gets the same fail-loud post-check (returns 500 with the same actionable message instead of fake `{deleted: true}`), keeping the dual-host contract consistent. Tool descriptions in `packages/core/src/i18n/{zh,en}.ts` updated to document the fail-loud contract and the new deletion order. 11 new tests: 4 in `test/dedup.test.ts` (stale-entry skipping for both `findExactHashMatch` and `buildHashIndex`), 3 in `test/tools.test.ts` (`engram_delete` fail-loud via Proxy-stubbed `deleteEngram`, plus a positive-path regression), 3 in `test/repository.test.ts` (deleteEngram ordering invariants — clean-index-on-return, file-already-missing idempotency, double-delete idempotency), 1 in `packages/viewer/test/viewer.test.ts` (DELETE endpoint fail-loud). Both hosts inherit the fix via shared core.

- **`engram_doctor` now cleans dangling references in derived indexes after external file deletions (`@co-engram/core`, `@co-engram/viewer`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: previously, when a user externally deleted an engram file (`git rm`, `rm`, IDE delete), `runDoctor()` cleared the stale entry from `engram-index.json` (the canonical map) — but the **derived** indexes `.co-engram/observation-windows.jsonl`, `.co-engram/digest.jsonl`, and `.co-engram/graph.json` still held references to the deleted ULID. Real-world symptom: `engram_search` returned stale hits, the viewer's effectiveness metrics counted interactions for memories that no longer existed, and `proposals.jsonl`-style files were the only ones correctly decoupled (they reference cluster IDs, not engram IDs). New `cleanupDanglingIndexReferences({ repo, dataRoot, canonicalIds })` runs as a **postflight** after `runDoctor()` (so the freshly-persisted `engram-index.json` is the source of truth): (1) filters `observation-windows.jsonl` in-place — JSONL lines whose `engramId` is not in the canonical set are dropped, malformed lines are kept (let audit / manual review handle them); (2) scans `digest.jsonl` and `graph.json` (nodes + edges) for dangling refs, and if any are found, triggers `IndexOrchestrator.fullRebuild()` to regenerate both atomically. New `DoctorIssue` kind `dangling_index_reference` extends the closed union; new i18n key `viewer.health.doctor.fixKind.dangling_index_reference` (zh + en) labels the kind in the viewer's doctor scan card. Files intentionally NOT touched: `topic-clusters.jsonl` / `proposals.jsonl` (reference cluster IDs, not engram IDs), `prompt-signals.json` (tag strings), `audit.jsonl` (append-only history). 8 new tests in `packages/core/test/index-cleanup.test.ts`. Both hosts inherit the fix via the shared `engramDoctorTool` — no adapter changes needed beyond rebuilding `dist`.

### Tests

- Trust-boundary redesign coverage: 7 new tool-level contract tests in `test/proposal-external-markdown.test.ts` (caller-omitted fields fall back to payload, override precedence, `createdBy` resolution chain, end-to-end `engram_search` hit after accept, `list_proposals` exposes `acceptedEngramId` / `sourcePath`, double-accept throws). 5 new tests in `test/repository.test.ts` lock watcher safety semantics (scanForExternalMarkdown does not trigger auto-rebuild, E2E accept readable, dismiss is permanent, post-merge reconciliation, watcher does not re-propose accepted files).

## [0.1.0] - 2026-06-21

### Summary

First public release. 22 tools, 1039 tests, 18k LOC of non-test TypeScript. Stable core with Claude Code (MCP) and OpenClaw (plugin) adapters. Automatic maintenance engine (light/deep/rem stages).

### Added

- **Core (`@co-engram/core`)**: engram lifecycle (create/get/update/delete/search/list/reinforce/report_failure/archive/restore/forget/recompute_importance), synapse graph (create/get/list/delete), skills (get/invoke), learning loop (close_learning_loop/contradiction_resolve/upgrade_verification/get_evolution_lineage)
- **Retrieval**: in-memory full-text search (CJK bigram + English word tokenizers) over a `digest.jsonl` catalog, graph traversal via synapse edges, multi-factor scoring (relevance/recency/importance/reinforcement)
- **Maintenance engine**: `light` stage (RPE-based reinforcement), `deep` stage (consolidation + Ebbinghaus decay), `rem` stage (metacognition with 5-dimension truth scoring)
- **Signals**: `FileSignalSink` (JSONL), 6 behavioral extraction rules, RPE computation
- **Verification**: 5-dimension metacognition (cross-context/time-stable/mutually-supported/source-reliable/executable), state machine with `force` override
- **Claude Code adapter (`@co-engram/claude-code`)**: MCP server with stdio transport, env-var-based maintenance config
- **OpenClaw adapter (`@co-engram/openclaw`)**: plugin SDK entry, manifest config schema, `contracts.tools` declaration for all 22 tools
- **E2E tests (`@co-engram/e2e`)**: dual-host consistency, maintenance scenarios, signal persistence
- **Documentation**: bilingual README (English + 中文), 10 deep-dive docs, 3 runnable examples
- **Community**: CONTRIBUTING, CODE_OF_CONDUCT, SECURITY, CHANGELOG, GitHub Actions CI, issue/PR templates

### Known Limitations

- `skill_invoke` is a framework only — concrete template execution (tool-sequences, prompt-templates) lands in a future release
- REM abstraction stage uses LocalHeuristic only — LLM-driven abstraction is planned but optional
- No Web UI — use Git/GitHub to browse the data repo
- No auto-generated tool reference from TSDoc — hand-written `docs/tool-reference.md` instead

### Breaking Changes

None (first release).
