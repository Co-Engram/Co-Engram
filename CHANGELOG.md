## [Unreleased]

### Changed

- **`computePromptSignals` N+1 `readEngram` eliminated via `readDigestBatch` (`@co-engram/core`)**: the maintenance light stage (5-min `setInterval`) calls `computePromptSignals(repository, …)` to refresh the prompt-builder's `lowConfidenceTopics` input. The previous implementation looped `repository.readEngram(entry.id)` for every catalog entry — at 1026 engrams each `readEngram` is `readFileSync` + YAML parse + `assembleEngram` (which itself scans the `synapses/` directory), and the loop synchronously blocked the gateway's single-threaded event loop for 30+ seconds. Real-world symptom: the viewer's HTTP endpoints were healthy in the first 5 minutes after `mcp-server` boot, then every `curl http://127.0.0.1:18799/...` started returning `000` (timeout) exactly when the light stage first fired, and stayed unresponsive until the stage finished. CPU pegged at 90%+ on one core, ProcessLock heartbeat starved, and external clients (curl, browser) saw the gateway as dead. The fix has two parts. (1) **`DigestLine` interface gains `confidence: number`** — the SQLite `engrams` table and `DigestIndexRow` already carried `confidence` (since schema v2), but the public `DigestLine` interface and the `digestRowToLine` mapping silently dropped it, so callers needing `confidence` had no batch path and were forced back to `readEngram`. The field is now projected by `digestRowToLine` (SQLite mode), `readDigestLine` (single-id helper in `index/digest-builder.ts`), and the `readDigestBatch` memory-mode fallback. One in-repo caller constructing a `DigestLine` literal by hand (`readEngramViewAuto` in `packages/core/src/tools/engram-tools.ts`) is updated to pass `confidence: 0` (the value is unused downstream by `adaptiveDisclosure`). (2) **`computePromptSignals` now batches via `repository.readDigestBatch(ids)`** — 500 ids per call (the API's per-call upper bound) so a 1026-engram warehouse is two SQL `WHERE id IN (?,?,…)` round-trips instead of 1026 `readEngram` calls. SQLite mode measures ~25ms total (1000x+ speedup over the 30+s N+1); memory-mode fallback still walks `readEngram` per-id but only matters for tiny warehouses where the cost is bounded. The previous "代价是 N 次 fs 读,light stage 5 分钟一次可接受" comment is removed — it was wrong at 1k+ scale. Tests: all 11 cases in `packages/core/test/prompt-signals.test.ts` pass unchanged (the public contract is identical); full core suite (2085 tests) green; manual live verification confirms the viewer stays responsive across the light-stage boundary (every 30s curl sample returns HTTP 200 in <50ms before, during, and after the stage fires).

- **Viewer performance + usability fixes for proposal/audit/graph tabs (`@co-engram/core`, `@co-engram/viewer`)**: four user-reported issues addressed. (1) **P0 — `ProposalEngine.readProposals()` / `readClusters()` now memoize on file `mtime` via `statSync`** before falling through to `readJsonl`. At 9.4MB `proposals.jsonl` (2044+ candidates) and 13 in-process call sites, every cache-less read blocked the gateway's single-threaded event loop long enough to starve the ProcessLock heartbeat `setInterval` past its 90s stale threshold — holders never fired `onLost`, dead holders kept the lock forever, and `/api/stats` / `/api/proposals` / `/api/audit` all timed out (curl `000`, viewer unreachable). The fix returns the cached array when `statSync().mtimeMs` matches the last read; `writeProposals()` / `writeClusters()` invalidate the cache. Measured impact (verified live on `18799`): audit P50 dropped from multi-second hangs to ~20ms; proposals P50 to ~7ms; the viewer is responsive immediately after `mcp-server` restart. (2) **P1a — Graph tab gains a top filter bar with keyword search + directory filter**: new `<input type="search" id="graph-q">` filters vis-network nodes by title/domainTags/id; a "📁 Filter by directory" button opens a drawer reusing `/api/path-tree` to pick a directory; selecting one keeps only nodes whose `id` starts with the chosen path prefix, with edges filtered to those whose `from` AND `to` both survive. Active filters render as removable chips; a live count chip shows `Nodes N · Synapses M`. Toolbar `reset()` clears the top filter alongside the kind checkboxes. New i18n keys (`viewer.graph.filter.*`, zh + en). (3) **P1b — Proposals tab card UX upgraded to match Engrams**: each card now shows kind-colored left border, ⚡ occurrences chip, 💬 sample-count chip (when `sampleQuotes` exist), full `payload.domainTags` chips (up to 4 + "+N"), and a longer 140-char preview; the empty state switches from a terse `✓` to a 🌱 icon plus a friendly hint ("the system observes candidate memories in the background…"). New i18n keys (`viewer.proposals.emptyHint`, `viewer.proposals.card.*`, zh + en). (4) **P1c — New lightweight endpoint `GET /api/engrams/ids`**: the Audit tab's `load()` previously called `/api/engrams?limit=500` to fetch 500 full digests (~100KB) only to derive `_existingIds` for the "is this engramId still alive?" badge on each audit row. The new endpoint returns just `{ ids: string[], total }` (~7KB at 1026 engrams), cutting first-paint by 50–100ms. The Audit tab's `Promise.all` is updated; existing `/api/engrams?limit=500` callers (engrams tab, etc.) are untouched.

- **Audit log now self-rotates by action value tier + file size hard cap, decoupled from the maintenance engine (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: previously `.co-engram/audit.jsonl` was append-only with no expiry — at sustained tool-call throughput (1000+ engrams × daily propose/reinforce/importance_update events) the file grew unbounded, and the existing `index-cleanup.ts` code path explicitly skipped it with a "不应清理" comment. The new rotation mechanism lives entirely on `AuditLog` and runs as an **independent background `setInterval`** (default 24h, `intervalMs` configurable), explicitly decoupled from the maintenance engine's light/deep/rem/daily stages per the design directive that "日志管理与 engram 数据维护是不同概念的东西". Two-axis retention: (1) **Action value tiering** — `HIGH_VALUE_ACTIONS` (create / update / update_lifecycle / importance_update / forget / restore / sweep_to_trash / restore_from_trash / purge / accept / dismiss / contradicted / merge_* / learning_loop_*) retain `highValueRetentionDays` (default 365d); everything else (propose / reinforce / report_failure / retrieve_* / noise_filtered / necessity_rejected) retains `retentionDays` (default 90d). (2) **File size hard cap** — even when no time threshold has tripped, `maxSizeMb` (default 50MB) forces tail-truncation (walk from the file's end, accumulate lines until the budget is exhausted) so `readFileSync` can never blow up on a runaway audit file. **Atomic write** via `tmp-${pid}-${ts}` + `renameSync` prevents partial-flush corruption. **Corrupt-line preservation**: lines that fail JSON.parse or have unparseable `ts` are kept verbatim, not silently dropped — hand-off to `engram_audit_query` / human review. **Failure mode is fail-soft**: every IO/JSON exception returns `{droppedCount: 0, originalSize, newSize: originalSize}` instead of throwing, and the rotation action itself never writes an audit entry (would be self-reinforcing noise). **Host wiring**: `createCoEngramMcpServer` and `registerCoEngramTools` both start the rotator after `auditLog` construction (skipped when `auditEnabled=false`), each returns a `stopAuditRotation` fn that the Claude Code MCP `shutdown` handler calls alongside `stopMaintenance` / `stopIndexWatcher`; the OpenClaw plugin relies on the timer's `unref()` for OS-level cleanup. **New types/exports**: `AuditRotationConfig` extracted as named interface (was inline in `AuditSectionConfig`); `DEFAULT_AUDIT_CONFIG` + all `DEFAULT_*_CONFIG` constants now re-exported from `@co-engram/core` public surface; `CoEngramMcpServerConfig.auditRotationConfig` and `CoEngramPluginConfig.auditRotationConfig` added (optional, falls back to `DEFAULT_AUDIT_CONFIG.rotation`). **Comment in `index-cleanup.ts` updated**: the stale "不应清理" note is replaced with a pointer to the new `AuditLog.startAutoRotation` path. **9 new tests** in `packages/core/test/audit-rotation.test.ts` lock the matrix (retentionDays drops low-value expired / highValueRetentionDays keeps old accept / maxSizeMb truncates tail-newest / corrupt-line preservation / noop when nothing to drop / empty-file no-throw / missing-file no-throw / `intervalMs<=0` returns noop-stop / `intervalMs>0` returns valid stop).



- **Viewer `GET /api/engrams` rewritten from N+1 `readEngram` loop to a single SQL query (`@co-engram/core`, `@co-engram/viewer`)**: at 1k+ engram scale the viewer's list endpoint was effectively unusable — the previous implementation called `repository.listEngrams()` (returns `EngramCatalogEntry[]` without `summary` / `importance` / `retrievalCount` / `visibility`) and then issued one `repository.readEngram(id)` per row to assemble the response payload. Each `readEngram` is a sync `readFileSync` + YAML parse + delocalize-keys pass, so 1k engrams ≈ 1k syscalls on the gateway's single-threaded event loop, blocking MCP tool calls and HTTP requests alike for 30+ seconds. Real-world symptom: after a load test seeded 1000 engrams, `curl /api/engrams` returned `000` (8s timeout) and the gateway process pegged one core at 95%+ CPU for minutes. The fix has three parts. (1) **Schema v2** for the derived `index.db`: the `engrams` table gains three columns that were previously only on the file's frontmatter — `summary TEXT NOT NULL DEFAULT ''`, `retrieval_count INTEGER NOT NULL DEFAULT 0`, `created_at INTEGER NOT NULL DEFAULT 0` — plus two indexes (`idx_engrams_created ON engrams(created_at DESC)` and `idx_engrams_retrieval ON engrams(retrieval_count DESC, updated_at DESC)`). A new `schema_version` table tracks the active version; on `IndexDb.open()` any version mismatch triggers a `DROP TABLE engrams` + full rebuild (SQLite is derived data, so DROP+rebuild is simpler and safer than `ALTER TABLE … ADD COLUMN`). `BootstrapResult.indexDb` is held by the host so it can be `close()`'d explicitly. (2) **`IndexDb.queryEngrams()`** replaces the per-row `readEngram` calls with one parameterized SQL query: `WHERE` clause filters by domain tags, kind, status, freshness, importance range; `ORDER BY` supports `updatedAt` / `createdAt` / `importance` / `retrievalCount` (each DESC + `id ASC` tiebreaker for stable pagination); `LIMIT ? OFFSET ?` (or cursor-keyed for pagination). Two new helpers, `encodeQueryCursor(sortValue, id)` and `decodeQueryCursor(cursor)` (named separately from the existing `encodeCursor` in `index-db-cursor.ts` because the cursor encoding is sort-key-specific), produce opaque base64url tokens stable across concurrent writes. (3) **`EngramRepository.queryEngramsForList()`** is the new public method the viewer calls — when `indexDb` is injected (sqlite engine active) it proxies directly to `IndexDb.queryEngrams()`; when not (memory fallback), it assembles the same `{ results, total, nextCursor }` shape from the in-memory path. The viewer's `GET /api/engrams` handler now calls `ctx.repository.queryEngramsForList(...)` and returns the cursor as `nextCursor`; default `limit=200`, max `limit=500`. The cold-start rebuild in `bootstrapRepositoryAndSearch()` also feeds the three new columns via `engramToIndexEntry()` so a fresh `index.db` against a non-empty warehouse is immediately sortable by `createdAt` / `retrievalCount`. **Measured impact** (1446 engrams indexed, `limit=500`): P50 ≈ 5ms, P95 ≈ 13ms, max ≈ 22ms — versus the previous 30+ second hang at 1k scale. Cursor pagination round-trip (`?limit=3&cursor=…`) adds <3ms. FTS search (`/api/search`) is unaffected (already sqlite-backed) and stays in the 3–22ms range. The viewer's frontend (`packages/viewer/src/runtime/tabs.ts`) caches `data.total` from the first page so the count chip renders the true total immediately; the audit tab drops its previous `?limit=10000` hack and uses the default paginated query. Note: this fix targets the *list* path; the graph tab's `buildGraph` still uses N+1 over the synapse layer and will be addressed separately.

- **Default search engine flipped from `memory` to `sqlite` with fail-safe fallback (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: `resolveSearchEngineType()` now defaults to `sqlite` and treats only the literal `CO_ENGRAM_SEARCH_ENGINE=memory` as opt-out (was: defaulted to `memory`, opt-in via `=sqlite`). Rationale: `sqlite` matches or beats `memory` at every scale (small-scale cold start is a few dozen ms; large-scale stays sub-100ms where `memory` blows past 1s), and the opt-in flag was failing the zero-friction default — 99% of users never set env vars and never experienced the optimization. Three safety rails land in lockstep with the flip: (1) `bootstrapRepositoryAndSearch()` wraps the entire sqlite branch in `try/catch` — if `IndexDb.open()` or the cold-start `rebuildFromEntries()` throws (Node version boundary < 22.17, file system permission error, schema corruption, disk full), the indexDb is closed and the host transparently degrades to `memory`; `engineType` in `BootstrapResult` reflects the *actually-active* engine, not the *wanted* one. (2) Boot now logs `[co-engram] search engine: sqlite (cold-start: yes, N engrams indexed in Mms)` or `... cold-start: no, N engrams already indexed` so the active engine is observable; on fallback it logs `[co-engram] search engine: sqlite unavailable (<reason>), falling back to memory`. (3) `engines.node` tightened from `>=22.0.0` to `>=22.17.0` across all 7 packages (root + 6 workspaces) — `node:sqlite` was experimental before 22.5 and only stabilized at 22.17. Users on older Node silently fall through to the `memory` fallback rather than crashing at boot. The `CO_ENGRAM_SEARCH_ENGINE=memory` opt-out remains as an escape hatch for embedded / read-only-fs / sandboxed deployments where the `index.db` side-effect is undesirable. Unknown env values now fall back to `sqlite` (was: `memory`) — a typo no longer silently downgrades you to the less-scalable backend. Tests: `packages/core/test/retrieval/engine-flag.test.ts` rewritten — `resolveSearchEngineType` default case + unknown-value case both flipped to `sqlite`, new explicit `=memory` opt-out case added; bootstrap memory-mode test now passes `env: { CO_ENGRAM_SEARCH_ENGINE: "memory" }` explicitly; cold-start test's first bootstrap flips to explicit memory (so the second sqlite bootstrap actually triggers cold-start rebuild rather than hitting hot-start no-op); new "default = sqlite" bootstrap test added at the top. README + README.zh-CN env tables updated bilingually (default column flipped, descriptions rewritten to describe fallback semantics); `docs/architecture.md` + `docs/architecture.zh-CN.md` Search Engine section restructured (sqlite = default + scaling path with fail-safe fallback + Node version requirement; memory = opt-out for restricted deployments) and the `index.db` bullet in the data-layout section relabeled as default-since-0.2.0.

- **`engram_list` / `engram_audit_query` / `engram_list_proposals` now use cursor pagination with required `limit`

- **`engram_list` / `engram_audit_query` / `engram_list_proposals` now use cursor pagination with required `limit` (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: previously these three list tools had optional `limit` (defaulting variously to 100 / 1000 / no-cap) and returned ad-hoc shapes — `engram_list` returned `{ results, total }`, `engram_audit_query` returned `{ events, count }`, `engram_list_proposals` returned `{ proposals, total }`. At 5k+ engram scale returning unbounded lists both burns tokens and creates unstable offsets when new entries arrive mid-pagination. The three tools now share a uniform cursor-paginated shape: `{ limit: number (required, 1-500 for engram_list/engram_list_proposals, 1-1000 for engram_audit_query), cursor?: string | null }` → `{ items: [...], nextCursor: string | null }`. The `cursor` is an opaque base64url token; pass it verbatim to the next call's `cursor` parameter to fetch the next page; `nextCursor === null` means no more results. Stable sort orders: `engram_list` sorts by `importance DESC, updatedAt DESC, id ASC`; `engram_list_proposals` by `createdAt DESC, entityId ASC`; `engram_audit_query` returns newest N within the filter (cursor encodes the oldest entry's `ts`, mutually exclusive with `until` — cursor wins). The OpenClaw adapter's `renderListResult` in `packages/openclaw-plugin/src/adapter.ts` is split into `renderListResult` (legacy `{ results, total }` shape, used by `engram_search`) and `renderCursorListResult` (new `{ items, nextCursor }` shape, used by the three refactored tools); the latter renders pagination hints when `nextCursor !== null`. The OpenClaw adapter's `engramListSchema` JSON Schema makes `limit` required and adds `cursor`. `engram_list_paths` keeps its existing `maxDepth` shape (no cursor — directory tree returns in one shot). This is a breaking change at the tool-input level; the affected callers (in-repo `packages/claude-code-mcp`, `packages/openclaw-plugin`, `packages/core/test`, and the `engram_audit_query` description) are all updated; no third-party callers exist. Users invoking these tools interactively via the LLM see no change — the LLM adapts its tool-call arguments from the updated JSON Schema automatically. `docs/tool-reference.md` + `docs/tool-reference.zh-CN.md` updated bilingually for all three tools; `docs/data-format.md` + `docs/data-format.zh-CN.md` archive-sweep example updated. Tests: `packages/core/test/audit-query-tool.test.ts` rewritten with cursor coverage; new cursor-stability tests appended to `packages/core/test/proposal-external-markdown.test.ts`; `packages/core/test/tools/engram-list-tool.test.ts` (cursor coverage added in earlier task); all `engramListTool.execute` / `listByFilter` / `listByImportance` callers in `packages/core/test/tools.test.ts` + `packages/core/test/retrieval.test.ts` updated to new shape.

- **First-time data root setup UX: viewer now offers one-click suggestions + non-engram dir takeover confirmation (`@co-engram/core`, `@co-engram/viewer`)**: previously the viewer's Config tab blindly rejected any non-empty non-co-engram directory with a terse "use the CLI with `--force`" message — locking first-time users out of the most natural flow (pointing at an existing project folder like `~/Documents/team-memory` that happens to already contain a README). `applyDataRootChange()` in `packages/core/src/bootstrap/classify.ts` now returns `existingFiles` (up to 10 entries) + `existingCount` on the `non-engram` failure result; the viewer's `PUT /api/config` accepts a new `force: true|false` body field and passes it through; the `saveDataRoot(force)` UI flow in `packages/viewer/src/runtime/tabs.ts` renders a confirmation banner listing the existing files (as `<code>` chips) plus a "Take over this directory" button — clicking it re-POSTs with `force: true`, which initializes the warehouse (writes `.co-engram/config.json`) without touching any user file. Co-ownership is safe by construction: co-engram only ever writes inside the `.co-engram/` subfolder. The CLI `--force` semantics are unchanged; the UI now exposes the same capability bilingually. On first open (no data root set), the Config tab additionally shows a welcome card with two one-click suggestions (`~/team-memory` recommended, `~/.co-engram-data` hidden) sourced from `GET /api/config`'s new `suggestedPaths` field (computed server-side from `process.env.HOME`). New i18n keys (zh + en): `viewer.config.dataRootNonEngramConfirmTitle/Body/ExistingList/More`, `viewer.config.dataRootTakeOver/TakeOverConfirm/Cancelled`, `viewer.config.dataRootWelcomeTitle/Body/SuggestHome/SuggestHidden/Custom`. `viewer.help.opsDataRoot` rewritten in both READMEs and help panel to describe the new flow. 6 new core tests in `test/bootstrap-classify.test.ts` lock the missing/empty/engram-warehouse/non-engram-with-force/empty-path-still-invalid matrix; 4 new viewer integration tests in `test/viewer.test.ts` cover the `PUT /api/config` force path end-to-end plus `suggestedPaths` on GET.

- **Proposal dismiss is now permanent by default + viewer no longer prompts for reason (`@co-engram/core`, `@co-engram/viewer`)**: previously dismissing a pending proposal set `dismissedUntil = now + 30d` (configurable via `defaultDismissDays`, default 7 in `DEFAULT_PROPOSAL_CONFIG`, 30 in `DEFAULT_DISMISS_DAYS`) and the dismissed proposal could re-surface after the cooldown expired — meaning users kept seeing the same candidate they had already rejected. Worse, `ProposalEngine.proposeAutoMemory()` re-opened dismissed proposals when the source `.md` file's payload changed, defeating the user's intent. The new behavior: `dismiss()` treats `dismissDays = 0 / undefined` as **permanent** (leaves `dismissedUntil = undefined`); `proposeAutoMemory()` short-circuits any dismissed proposal regardless of payload change (auto-memory source files changing no longer resurrect rejected candidates); `observe()` keeps the time-limited-reactivation path only when an explicit `dismissDays > 0` was supplied. `DEFAULT_PROPOSAL_CONFIG.defaultDismissDays` and `defaults.ts` `defaultDismissDays` both flip to `0` (permanent). The viewer's `dismissFromForm()` drops the two `prompt()` calls (reason + days) — it now uses a single `confirm()` with a bilingual message ("确认驳回此提案?驳回后将不再出现,审计日志保留。" / "Dismiss this proposal? It will not resurface. Audit log retained.") and posts an empty body so the backend uses the permanent default. i18n keys `viewer.proposals.dismissReasonPrompt` and `viewer.proposals.dismissDaysPrompt` are removed; new key `viewer.proposals.dismissConfirm` is added (zh + en). Tool descriptions (`tool.engram_dismiss_proposal` short / `.agent` / `.technical`) and the in-source `proposal-tools.ts` short description are updated to reflect "permanent by default, dismissDays > 0 opts into N-day reactivation". `engram_dismiss_proposal` remains fully backwards-compatible at the API level — callers passing `dismissDays: 30` still get a 30-day reactivatable dismiss; the change is purely about what happens when the field is omitted. Audit log always retained regardless of dismiss flavor.
- **Claude Code auto-memory sync now produces proposals instead of engrams (`@co-engram/claude-code`, `@co-engram/core`)**: previously the auto-memory watcher directly created engrams in the team repo for every `.md` file under `~/.claude/projects/*/memory/`, bypassing the user-review gate that `ProposalEngine` imposes on every other capture path. The new `ProposalEngine.proposeAutoMemory()` method writes pending proposals (with `source: "auto-memory"` + full payload: title/content/domainTags/kind/visibility/...) to the same `proposals.jsonl` store; the user/LLM then triages via the existing `engram_accept_proposal` / `engram_dismiss_proposal` tools. `engram_accept_proposal` now allows omitting `title`/`content`/`domainTags` when the proposal carries a payload (auto-memory source); conversation-source proposals are unaffected (payload stays `undefined`, original required-field behavior preserved). The `Proposal` interface gains optional `source` / `slug` / `payload` fields — existing proposals.jsonl entries without these fields are read as `source: "conversation"` (backwards compatible). `AutoMemorySyncEngine` constructor drops the `repository` dep and takes `proposalEngine` instead; startup log line now reads `(initial: N files, M proposed, K updated)` (was `created`). The `engram_create` tool description's auto-memory warning is rewritten — the old "pushes that path into the team repo unconditionally" framing no longer holds.
- **`engram_search` / `engram_list` / `engram_audit_query` filter now strictly rejects unknown keys (`@co-engram/core`)**: previously the Zod `SearchFilterSchema` used default strip mode, so a typo'd filter field (e.g. `createdInsread` instead of `createdBy`) was silently dropped — every engram then matched the empty filter and the user got the full list back without realizing their filter never applied. The schema now uses `.strict()` to reject unknown keys with a clear Zod error. Same `SearchFilterSchema` also gains a `contextTags: string[]` field (semantic matches `domainTags`: engram passes filter when any `contextTags` value intersects); previously this field was missing from the interface / Zod schema / `matchesFilter` in lockstep, so `contextTags` queries were also silently stripped. The strict-mode rejection is the user-visible breaking change, so any caller that previously sent unknown filter fields will now get a validation error instead of a too-many-results list.
- **ULID fields are now case-insensitive at the schema layer (`@co-engram/core`)**: the Crockford base32 ULID spec is case-insensitive, but `engram_get` / `engram_reinforce` / `contradiction_resolve` rejected lowercase ULIDs with `INVALID_ID` because no normalization was applied. Some markdown renderers, URL encoders, and shell variable expansions downcase ULIDs. New `normalizeUlid()` helper uppercases input at the Zod schema layer via `.transform()`, applied to `EngramGetInputSchema.id`, `EngramReinforceInputSchema.id`, `ContradictionResolveInputSchema.fromId`, `ContradictionResolveInputSchema.synapseId`. Existing uppercase ULIDs are unaffected.
- **OpenClaw adapter preserves `importance` / `freshness` / `contextTags` / `createdBy` in list renders (`@co-engram/openclaw`)**: the `renderListResult` function in `packages/openclaw-plugin/src/adapter.ts` previously dropped these four fields from each hit, leaving the OpenClaw-side agent with only `id` + `title` + `tags` + `summary`. The Claude Code MCP side already rendered the full object via `JSON.stringify`, so this was a pure dual-host contract inconsistency. The render now shows `importance` (2-decimal), `freshness` (raw enum), `contextTags` (comma-joined), and `createdBy` whenever present, with defensive fallbacks for the nested `metadata.*` shape used by `memory_search`.
- **ToolContext now carries a `host` marker (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: `createCoEngramMcpServer` injects `host: "claude-code-mcp"`, `createCoEngramContext` injects `host: "openclaw-plugin"`, and the value flows into `AuditEntry.host` for every audit append. Existing audit entries written before this change simply have `host: undefined` (backwards compatible). This is the first cross-host attribution seam — the audit log can now answer "did this `engram_reinforce` come from a Claude Code session or an OpenClaw session?" — fixing one of the long-standing dual-host contract gaps.
- **Chinese full-text search now indexes both word-level and unigram tokens for CJK segments (`@co-engram/core`)**: previously the `Intl.Segmenter` (granularity=word) emitted word-level tokens only, so a singleton CJK query like `"团"` failed to hit documents containing `"团队"` (the index had `"团队"` but not `"团"`). The `tokenize()` function in `packages/core/src/retrieval/fts.ts` now also emits each CJK character of any word-level segment of length > 1, so single-character queries hit as expected. Query-side tokenization is unchanged (segmenter behavior is identical), so existing multi-char queries still match the same docs.
- **`git commit` auto-sets `core.quotepath=false` on the local repo (`@co-engram/core`)**: Git defaults to `quotepath=true`, which octal-escapes non-ASCII paths in `git status` / `git show --name-only` output (e.g. `"\346\265\213\350\257\225.md"` instead of `"测试.md"`). The `commitFiles()` function in `packages/core/src/storage/git.ts` now runs `git config core.quotepath false` immediately after the git-repo check, so the subsequent `git show --name-only --pretty=format: HEAD` (used to compute `filesChanged`) returns human-readable Chinese paths. The config write is scoped to the local repo and fails soft (never blocks the commit).
- **Viewer `renderMarkdown` DOMPurify config tightened (`@co-engram/viewer`)**: the previous config had an `ALLOWED_TAGS` allowlist but no URI protocol restriction, so `<a href="javascript:alert(1)">` and similar payload links rendered as clickable. ### Fixed

- `engram_doctor` and `engram_list_paths` no longer throw when called through the MCP server or the OpenClaw plugin — the host adapters now inject the repository by default.
- **`SqliteSearchOrchestrator.buildFtsQuery` now splits multi-token queries into OR-connected phrases instead of wrapping the whole query as a single phrase, restoring recall for combined queries like `"co-engram loop 模式"` / `"挑剔用户 改进循环"` (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: the previous implementation wrapped the entire query string in `"..."` (FTS5 phrase syntax), which the trigram tokenizer expands into 3-char windows that span spaces. The phrase match then required the document to contain the *exact contiguous character sequence* of the query — so any multi-token query (Chinese-mixed-with-English, or two concepts separated by a space) returned 0 hits even when every individual token appeared in thousands of engrams. Real-world symptom: `engram_search("co-engram loop 模式")` against a 1026-engram warehouse returned `[]` despite the top hit's title being literally `"co-engram 改进循环（挑剔用户 loop 模式）"`. The fix splits the query on whitespace + CJK punctuation into tokens, wraps each token as its own phrase (so `"..."` still handles `-` / `_` / `.` inside tokens like `co-engram`), and joins them with `OR` — partial matches now recall, and bm25 ranks documents hit by more tokens higher. A secondary LIKE fallback (already in place) catches the residual blind spot where OR still returns 0 (e.g. all tokens are absent). 4 new regression tests in `packages/core/test/retrieval/sqlite-orchestrator.test.ts` cover: Chinese-mixed-with-English multi-token recall, partial-token-match recall, double-quote escaping inside tokens, and bm25 non-zero score assertion for rare-token hits (guards against the false-positive "score 0.000 = LIKE fallback" reading when a common token's IDF drives bm25 near zero). Both hosts inherit the fix via the shared `SqliteSearchEngineAdapter` with zero adapter changes.
- **`AuditLog.query` now returns entries in time-ascending order (old → new), matching the `engram_audit_query` tool's documented contract (`@co-engram/core`)**: the streaming + ring-buffer rewrite (see the `### Changed` entry above) ended each `query()` call with `ringBuf.reverse()`, supposedly "to match the old implementation" — but the old implementation never returned reverse order either, and the new `engram_audit_query` tool's description explicitly promised "items 按时间正序" (time-ascending). The result was that LLM-driven audit queries (`engram_audit_query` tool), programmatic callers (`engram_audit_query` direct invocations), and the merge-coordinator stress test all received entries newest-first when they expected oldest-first — pagination cursors (encoded as the oldest entry's `ts` for the next page's exclusive `until` boundary) produced the wrong slice, and the cursor-tie-break test `entries[i].ts >= entries[i-1].ts` failed on every multi-entry page. The fix is a one-line change: `return ringBuf` instead of `return ringBuf.reverse()`. The ringBuf is filled in scan order = file append order = write-time order, so without the spurious reverse it is already time-ascending. **Why the viewer is unaffected**: `GET /api/audit` calls `paginateWithCursor({ items, descending: true, getSortKey: x.entry.ts })`, which re-sorts the entries itself, so the query's return order was never load-bearing for the viewer. The fix is a pure contract alignment for the audit-query tool path.
- `EngramRepository.listPathTree()` now returns root node with `path: '/'` (was empty string), matching POSIX path conventions and making the output friendlier for LLM consumption.
- **`CO_ENGRAM_DEFAULT_CREATED_BY` environment variable is now actually read** (previously documented but silently ignored). The MCP server resolves `createdBy` default with priority: env `CO_ENGRAM_DEFAULT_CREATED_BY` > `team-memory.json` persisted config's `defaultCreatedBy` > fallback to `'unknown'`. As part of the same fix, `engram_create` / `synapse_create` `createdBy` field changed from required to optional, with the resolved default injected through `ToolContext.defaultCreatedBy`. The OpenClaw adapter already had this wiring through its config schema (`defaultCreatedBy`, default `'openclaw'`); it now correctly forwards the value into `ToolContext`. Dedupe `UPDATE` path also uses the resolved value as `mergedBy`. New helper `getDefaultCreatedByFromEnv()` is exported from `@co-engram/claude-code` for host integrators.
- **`invalidateSearchIndex` is no longer a no-op** — previously after `engram_create` / `engram_update` / `engram_delete`, the in-memory `SearchOrchestrator` index was stale (a startup snapshot), so the LLM would immediately search for a just-created engram and get zero hits, falsely concluding the write failed. The function now rebuilds the index from `repository.listEngrams()` on every write. Cost is O(N) per write (acceptable for N < 10k); a future release will switch to incremental updates.
- **`standard` tool profile now includes `engram_doctor` and `engram_list_paths`** (count 14 → 16). Previously these were locked to `full` profile despite being core user-facing features (self-healing scan + progressive directory disclosure). The LLM under default profile can now call them directly without reconfiguring.

## [0.1.5] - 2026-07-03

### Changed

- **Trust boundary redesign: data-root `.md` files now become proposals (not engrams) on watcher fire, while `git pull` is trusted as an explicit user action (`@co-engram/core`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: previously the `dataRoot` recursive watcher treated any `.md` write under the data root as a "create engram" trigger — but a watcher firing on a file the user did not hand-author (an external tool, an LLM recovering from a crash, or `git pull` checking out a teammate's commit) is not the same trust tier as a deliberate `engram_create`. Two failure modes followed: (1) `git pull` checked out a teammate's commit but the watcher re-proposed every incoming `.md` (or worse, raced with `git pull` mid-checkout), polluting the proposal queue with duplicates of engrams that already existed; (2) when a stale-state file under `dataRoot` was rewritten by an external process, the watcher again re-proposed it, defeating the user's dismiss intent. New `ProposalEngine.proposeExternalMarkdown()` is the single entry point for "I observed a `.md` file the user did not hand-author" — it writes a pending proposal (`source: "external-markdown"`, `slug` derived from path) instead of an engram; the existing watcher in `packages/claude-code-mcp/src/memory-sync/sync-engine.ts` and `packages/openclaw-plugin/src/plugin-entry.ts` now route `.md` writes through this method. The `createExternalMarkdownHook` helper installs the recursive watcher on `dataRoot` (filtering out `.co-engram/` subdirectory to avoid watching the index/proposals/audit files). `engram_accept_proposal` now allows omitting `title` / `content` / `domainTags` when the proposal carries a payload (external-markdown source), with the same fallback semantics as auto-memory proposals. The `Proposal` interface gains `source: "external-markdown"` as a new value alongside `"conversation"` / `"auto-memory"`; existing entries without the field are read as `"conversation"` (backwards compatible).

- **Post-merge git hook now runs `engram_doctor` so the canonical index reflects the teammate's commit before any other tool reads it (`@co-engram/core`)**: previously after `git pull` checked out a teammate's commit, `engram-index.json` was whatever the local repo had before the pull — so `engram_search` returned stale results, `engram_get` could miss just-pulled engrams, and the viewer showed a confusing mix of pre- and post-pull state until the next maintenance cycle. New `runPostMergeHook()` in `packages/core/src/merge/post-merge-hook.ts` runs after a successful `git pull` and (1) re-reads `engram-index.json`, (2) calls `runDoctor()` + `runInfraDoctor()` + `cleanupDanglingIndexReferences()` so any moved / renamed / deleted-by-teammate files are reconciled into the canonical index and derived indexes, (3) logs a summary. The hook is wired into the same `git` config slot as the merge driver; both hosts trigger it via the `git pull` wrapper in `repository.ts`. Combined with the watcher-redesign above, the new contract is: **`git pull` is trusted (it's an explicit user action); filesystem watcher is not trusted (it's ambient observation)**.

### Fixed

- **Three fail-silent bugs around `engram_delete` (`@co-engram/core`, `@co-engram/viewer`)**: user reported that `engram_delete` returned `{deleted: true}` but the entry stayed visible in the viewer — close inspection uncovered three distinct fail-silent failure modes clustered around the delete path. (F1) **`engram_delete` tool now post-checks the deletion**: when `repository.deleteEngram()` silently no-ops (cross-process race restores the file, `resolvePath` returns `undefined`, etc.) the tool previously returned `{deleted: true}` and wrote a misleading `purge` audit; it now re-checks `repository.exists(id)` after the call and throws `engram_delete failed: <id> still exists after deleteEngram (…run engram_doctor to self-heal)` so callers know to self-heal rather than trust a fake success. (F2) **`findExactHashMatch` / `buildHashIndex` now skip stale index entries**: when an engram file is removed externally but the index entry lingers (post-crash / partial delete), the previous `readEngram(entry.id)` threw and either aborted the whole dedupe pass or returned the dead id as a `DUPLICATE` target — locking the user out of recreating an engram with the same `contentHash`. Both functions now guard with `repo.exists(entry.id)` + try/catch around `readEngram`, skipping stale entries so dedupe falls through to similarity recall or `NEW`. (F3) **`deleteEngram` order changed from `file → synapse → index` to `index → file → synapse`**: the old order's mid-failure state left the index entry pointing at a deleted file (`dangling_index_entry`), which `doctor`'s `missing_file` check requires the file to actually be gone to detect — so a race that restored the file hid the inconsistency. The new order guarantees the index is clean when `deleteEngram` returns; any partial failure now lands in `doctor`-self-healable territory (`orphan_markdown` / `dangling_synapse`). The viewer's `DELETE /api/engrams/:id` endpoint gets the same fail-loud post-check (returns 500 with the same actionable message instead of fake `{deleted: true}`), keeping the dual-host contract consistent. Tool descriptions in `packages/core/src/i18n/{zh,en}.ts` updated to document the fail-loud contract and the new deletion order. 11 new tests: 4 in `test/dedup.test.ts` (stale-entry skipping for both `findExactHashMatch` and `buildHashIndex`), 3 in `test/tools.test.ts` (`engram_delete` fail-loud via Proxy-stubbed `deleteEngram`, plus a positive-path regression), 3 in `test/repository.test.ts` (deleteEngram ordering invariants — clean-index-on-return, file-already-missing idempotency, double-delete idempotency), 1 in `packages/viewer/test/viewer.test.ts` (DELETE endpoint fail-loud). Both hosts inherit the fix via shared core.

- **`engram_doctor` now cleans dangling references in derived indexes after external file deletions (`@co-engram/core`, `@co-engram/viewer`, `@co-engram/claude-code`, `@co-engram/openclaw`)**: previously, when a user externally deleted an engram file (`git rm`, `rm`, IDE delete), `runDoctor()` cleared the stale entry from `engram-index.json` (the canonical map) — but the **derived** indexes `.co-engram/observation-windows.jsonl`, `.co-engram/digest.jsonl`, and `.co-engram/graph.json` still held references to the deleted ULID. Real-world symptom: `engram_search` returned stale hits, the viewer's effectiveness metrics counted interactions for memories that no longer existed, and `proposals.jsonl`-style files were the only ones correctly decoupled (they reference cluster IDs, not engram IDs). New `cleanupDanglingIndexReferences({ repo, dataRoot, canonicalIds })` runs as a **postflight** after `runDoctor()` (so the freshly-persisted `engram-index.json` is the source of truth): (1) filters `observation-windows.jsonl` in-place — JSONL lines whose `engramId` is not in the canonical set are dropped, malformed lines are kept (let audit / manual review handle them); (2) scans `digest.jsonl` and `graph.json` (nodes + edges) for dangling refs, and if any are found, triggers `IndexOrchestrator.fullRebuild()` to regenerate both atomically. New `DoctorIssue` kind `dangling_index_reference` extends the closed union; new i18n key `viewer.health.doctor.fixKind.dangling_index_reference` (zh + en) labels the kind in the viewer's doctor scan card. Files intentionally NOT touched: `topic-clusters.jsonl` / `proposals.jsonl` (reference cluster IDs, not engram IDs), `prompt-signals.json` (tag strings), `audit.jsonl` (append-only history). 8 new tests in `packages/core/test/index-cleanup.test.ts`. ## [0.1.0] - 2026-06-21

### Summary

First public release. 22 tools, 1039 tests, 18k LOC of non-test TypeScript. Stable core with Claude Code (MCP) and OpenClaw (plugin) adapters. Automatic maintenance engine (light/deep/rem stages).

### Added

- **Core (`@co-engram/core`)**: engram lifecycle (create/get/update/delete/search/list/reinforce/report_failure/archive/restore/forget/recompute_importance), synapse graph (create/get/list/delete), skills (get/invoke), learning loop (close_learning_loop/contradiction_resolve/upgrade_verification/get_evolution_lineage)

- **Signals**: `FileSignalSink` (JSONL), 6 behavioral extraction rules, RPE computation
- **Verification**: 5-dimension metacognition (cross-context/time-stable/mutually-supported/source-reliable/executable), state machine with `force` override
